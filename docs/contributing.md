# Contributing locally

Use the pinned Node version in `.nvmrc` and pnpm version in `package.json`.
Work only in a repository-local `.worktrees/` checkout; dependencies and scanner
installation are per-worktree. `.npmrc` and the lockfile use only public npm.
Run `pnpm install --frozen-lockfile` and acquire the pinned scanner with
`node scripts/security/gitleaks.mjs install` when network acquisition is authorized.
The installer verifies archive and executable checksums; never fabricate integrity
values or weaken gates to accommodate a registry problem. It keeps the verified
archive in ignored `.airig/tools/gitleaks/<version>/archives/` and on a later install
re-verifies that archive against the pinned SHA-256 instead of downloading again.
A kept archive with wrong bytes, a symlink, a directory or an oversized file fails
closed with nothing extracted and is never silently replaced; delete it to download again.

## Adding a component

A component branch adds the component's own files, **one line** in `packages/docs/catalog.jsonl` and its changeset.
It edits no shared list: everything that used to be one is derived from the catalog and the component folders, so
parallel component branches merge with `main` without conflicts when merged with local git (see "Parallel component
branches" below for the supported way to update a pull request). `pnpm generate` (in `packages/velcro`) scaffolds the
component and the pieces below; fill them in, then run `pnpm sync` from the repository root.

The component's own files:

- `packages/velcro/src/components/<name>/`: the class, its styles, `class.ts` (the class-only entry with the `Sl*`
  alias) and the registering `index.ts`. Every `.ts` file there except `index.ts` and `class.ts` states its provenance
  in its header: `THIRD_PARTY_NOTICES.md` for adapted Shoelace material, otherwise that it includes no Shoelace source.
  `NOTICE.md` (optional) is the component's entry for `THIRD_PARTY_NOTICES.md`: a Markdown list item, like those in
  the root file's Shoelace section, naming the files in this folder that adapt Shoelace material. Every file it names
  must exist and cite `THIRD_PARTY_NOTICES.md` in its header, unless the entry marks it `(written for Velcro`
  (`checkProvenance` in `scripts/sync.mjs`). The package and site copies of the notices are assembled from the root
  file and these fragments at build time.
- `packages/docs/pages/components/<name>.ts`: the docs page.
- `packages/docs/examples/<name>/*.html`: at least one example that uses `<sl-<name>>`.
- `packages/docs/showcase/<name>.html`: the home page snippet, which uses `<sl-<name>>`.
- `tests/product/<name>.spec.mjs`: the browser spec. The generated skeleton fails until it is replaced with real checks.
  `tests/product/<name>.probe.json` (optional) is the content and attributes the inherited-API probe
  (`tests/product/inherited-api.spec.mjs`) puts on the element when filling its declared slots is not enough.
  The component's React wrapper checks go in its own spec too, with `tests/product/support/react.mjs` (a React 19
  page that renders any wrapper by name), not in the shared `tests/product/react.spec.mjs`.
- `tests/api/components/<name>.mjs` (optional): manifest checks for this component, registered by
  `tests/api/manifest.test.mjs` against its shared analysis.
- `tests/upstream/shoelace-2.20.1/src/components/<name>/<name>.test.ts` (when Shoelace ships one): the upstream test,
  vendored unmodified, and its record `tests/upstream/components/<name>.json` (`docs/conformance.md`).
- `docs/api/parity/<name>.md`: the component's API parity report, generated by `pnpm sync`.

The catalog line holds `name`, `title`, `tag` (which must be `sl-<name>`) and the selector the browser tests wait for
(`#id` or a tag name, which must match an element in the component's examples). Line order does not matter (entries
are read sorted by name; the generator inserts in order).

Derived from the catalog and the component folders, never edited by hand:

- `packages/velcro/package.json` `exports`: `./<name>`, and `./<name>/class` when the component has a `class.ts`,
  written by `pnpm sync` one entry per line. `.gitattributes` merges this file and the catalog with git's union
  driver, so two branches that each add a component keep both lines; the export map is checked as a set.
- `packages/velcro/src/index.ts` (the package root), `packages/velcro/custom-elements.json` and the package and site
  copies of `THIRD_PARTY_NOTICES.md`: build output, ignored by git.
- The docs navigation, home page, required site pages, browser routes and the tests' component lists.

`pnpm sync check` (also run by `tests/bootstrap/sync.test.mjs` in `verify:source`) fails when a committed derived
file is stale; `pnpm sync` is the fix for a stale file, including after a merge. A key that appears twice in
`package.json` is different: a union merge kept both sides of a line two branches edited, and only a person can tell
which side is right, so `pnpm sync check` reports it and `pnpm sync` refuses to run until it is resolved by hand.

### Parallel component branches

The union merge is applied by local git, which reads `.gitattributes` from the working tree. A merge done on the hosting
platform (a pull request's mergeability check, its "Update branch" button, its conflict editor or a merge queue) may not
apply it, and then shows the catalog and `package.json` as conflicting once another component lands. The supported way
to bring a component branch up to date is local:

```sh
git -C <worktree> fetch origin
git -C <worktree> merge origin/main     # union-merges the catalog and package.json
pnpm sync                               # refuses on union-merge damage; resolve that by hand
git -C <worktree> diff origin/main -- packages/docs/catalog.jsonl packages/velcro/package.json
```

The last diff must show only this component's catalog line and export lines. Then run the full verification and the
security checks for the exact resulting head, and push it; `main` is then an ancestor of the branch, so the platform's
own merge is a fast-forward or trivial merge with nothing to conflict. Do not use the web "Update branch" button or
conflict editor for these files, and run any merge queue with a group size of one (or update locally between merges).
The union attributes are a merge convenience, never an approval: every gate still runs on the merged head.

A module that Shoelace publishes next to a component (for example `dist/components/include/request.js`) is exported by its full key and only
if `MODULE_EXPORTS` in `scripts/site/catalog.mjs` lists it: once its component is in the catalog the entry is required, with exactly its
listed targets, and the gate rejects any other `./<name>/<subpath>`. A module that belongs to the package rather than a component
(`dist/utilities/localize.js` and the 29 `dist/translations/<code>.js` files) is listed with the owner `PACKAGE_OWNER`, and is
required whatever the catalog holds. `pnpm sync` writes these entries too.

The page's API tables are not hand-written: `apiReference('sl-<name>')` (`packages/docs/src/api.ts`) renders them from
the Custom Elements Manifest the build analyzes from the component's JSDoc (`@tag`, `@status`, `@slot`, `@csspart`,
`@cssproperty [--name=default]`, `@event`) plus the API inherited from `@charm-ux/core`. A component declares the
inherited core events it never emits with `@inheritedEventDropped <event> - <why>` and the inherited slots, parts or
custom properties that still apply with `@inheritedKept <slots|cssParts|cssProperties> <name> - <why>` on its class.
After changing a component's API run `pnpm sync` (and `node scripts/api/parity.mjs ledger` when a Shoelace gap was
closed; the ledger refuses new gaps). Tests fail when a page's tables, a parity report or the ledger drift.
`docs/api/shoelace-2.20.1.custom-elements.json` already covers every Shoelace component.

The coverage gate (`tests/bootstrap/catalog.test.mjs`, part of `verify:source`) fails when a component directory has no catalog
entry, an entry has no component, a docs page has no entry, an example selector matches nothing, an export is stray or has
wrong targets, or any piece above or the package export is missing. The page is published
automatically by the Pages workflow when the change is pushed to `main` (manual dispatch is the fallback); it refuses a site that lacks a catalog page.
Set `VELCRO_PRODUCT_PORT` (integer, 1024-65535, default 4321) to run the product tests on another port, so worktrees can
verify in parallel.

## Explicit checks

- `pnpm verify` runs `verify:source` then `verify:product`. `verify:product`
  builds the library, statically builds the docs (which generates the type inputs),
  type-checks the docs, then runs the
  Playwright suite in Chromium, Firefox and WebKit (at least eight tests in each
  engine, the same number per engine, no failures, flakes or skips, fresh report
  required). Raw output stays in ignored `.airig/product/`; on a browser failure only
  engine counts and, per failing test, the engine, spec file and line, title and
  failure category (matcher name or error class) are printed, never messages,
  values or page content.
  Install the browsers once with `pnpm exec playwright install chromium firefox
  webkit` (add `--with-deps` on Linux); they are never installed automatically.
  Tests must not rely on Chromium-only behavior (computed-style serialization,
  clipboard permissions, link Tab stops on macOS WebKit); where an engine
  genuinely differs, branch on `browserName` in the test and say why.
  Tests run fully parallel, so none may depend on another test's order or state.
  CI builds once and runs each engine in four Playwright shards plus the
  upstream gate as separate jobs (`.github/workflows/product.yml`), through
  `verify:product --stage build|browser|upstream|evidence`; locally, run
  `verify:product` without arguments.
- `pnpm verify:source`: pinned tools, complete executable hook files, real scanner,
  meaningful tests with zero skips, and the actual proposed index. Raw test output
  stays under ignored `.airig/verify/`; summaries contain no raw tool errors.
- `node scripts/security/privacy.mjs files <path...>`: working-copy content.
- `node scripts/security/artifacts.mjs <path...>`: explicit outbound **plain text**,
  such as a PR title/body or release notes saved as `.txt` or `.md` files. It runs
  the trusted privacy rules and the pinned Gitleaks scan over private in-memory
  snapshots of the exact bytes (numbered `.txt` copies, so stock path exclusions
  cannot apply; any exclusion or incomplete scan fails) and, when clean, prints
  each input's byte/line counts and SHA-256 plus an ordered-set hash. A clean
  result applies only to those exact bytes: send the same bytes you scanned, and
  rescan after any edit or tool-side reformatting. At most 16 inputs, 1 MiB each,
  4 MiB total. Directories, symlinks, special files, archives, images, binaries,
  other file types, empty, oversized, non-UTF-8 and unreadable inputs fail closed,
  and there are no options or skip flags. Output is fixed text (logical labels such
  as `outbound/text-1.txt`, rule names, line numbers, counts); matched text, input
  paths and raw errors are never printed. Exit 0 clean, 1 findings, 2 failure. This
  is **not** artifact, bundle, package or site certification, it never sends or
  uploads anything, and pattern scanning does not detect all credentials or personal
  data. Archives, screenshots and package/site artifacts remain gated.
- `node scripts/security/git-privacy.mjs staged`: all exact staged blobs/paths,
  including an alternate `GIT_INDEX_FILE`, never substituted working-copy files.
- `node scripts/security/git-privacy.mjs identity`: repository-local explicit
  approved identity and effective author/committer, including environment overrides.
- `node scripts/security/git-privacy.mjs message <file>`: exact message/footer text.
- `node scripts/security/git-privacy.mjs history [revision-or-range]`: raw commit
  metadata/messages (author, committer, other headers, message) for every commit in
  the selected tip's full ancestry, plus the content and path of every file a
  commit changed. Unchanged files are not rescanned: each commit contributes only
  the files it adds or modifies relative to its parents (a root commit: all files;
  a merge: every path whose result differs from every parent, so an evil merge's
  new content is scanned). In a range, a parent outside the range is replaced by
  the range base for this comparison, so content inherited from an older,
  unscanned ancestor is scanned unless the base tip has the same file. Deleted
  files need no content scan. Identical path/blob pairs are scanned once. With a
  single tip (full-history mode) content is checked across the whole ancestry
  under the hard caps only. With a range `<base>..<tip>`, content is checked for
  commits not reachable from `<base>`, which must be the fetched
  `refs/remotes/origin/main` or one of its ancestors (anything else fails with
  exit 2); metadata is still checked for the full ancestry. A range of more
  than 1,000 changed-file entries fails with exit 3 and `history scan exceeds
  1,000 changed files; owner approval required` (see "History scan approval").
  Success prints only counts. Replace refs, presentation settings and mailmaps
  cannot change inspected objects; shallow repositories and legacy grafts are
  refused.
- `node scripts/security/git-privacy.mjs pre-push [origin]`: consume Git's proposed
  updates on stdin; accept one feature-branch creation or fast-forward update to
  the same branch name on `origin`, never an ordinary direct push to `main`.
  Inspect the supplied full OID, not the current named local branch, and scan its
  full-ancestry metadata, ref name, and the changed files of every commit not
  reachable from the fetched `origin/main` (the range being published, under the
  1,000-entry approval cap). Require a direct, already fetched
  `refs/remotes/origin/main` commit included in that ancestry. For an update,
  require the exact fetched `refs/remotes/origin/<feature>` OID to match Git's
  proposed old OID; for creation, no existing fetched feature ref may conflict.
  Missing, stale, symbolic or non-commit baselines fail. Deletion, bulk/mirror,
  non-fast-forward, tag and other-remote updates are refused. This command never
  fetches: refresh trusted refs separately when authorized, then check again.
  The coordinator must use an explicit single feature refspec, never `--mirror`.
  Git's hook protocol exposes ref updates, not the original command flags:
  configured mirror mode and mirror/bulk ref sets are rejected, but an explicit
  mirror invocation that happens to propose only the same allowed update cannot
  be distinguished locally. Checking the authorized outbound command is still
  required; the hook is not a generic command-authorization system.
- `node scripts/security/git-privacy.mjs policy <base-oid> <head-oid>`: **report**
  protected scanner, policy, workflow, hook, test and identity/tooling changes,
  including edits later reverted. Exit 0 means the comparison completed, not
  content clearance or human approval. A protected-change notice does not block
  creating a privacy-clean PR branch; it requires separate human merge/publication
  review. The pre-push command emits the same notice after mandatory data checks.

### History scan approval

A published range (pre-push: commits not reachable from the fetched `origin/main`;
CI on a PR: the PR's commits against the fetched `origin/main`, whatever the PR's
base; CI on a merge group: the squashed commit against the fetched `origin/main`;
CI on `main`: the commits since the previous `main` tip) may contain at most
1,000 changed-file entries. Above that the
scan stops with exit 3 before inspecting content. Only the owner approves a larger
range, and only for one exact head:

- Locally: `VELCRO_HISTORY_APPROVED=<full head OID>` for that one command. Any other
  value, an abbreviated OID or a different head stays blocked. **Agents must never
  set this variable**, suggest a value for it, or retry a blocked push with it; stop
  and report the exit instead.
- In CI: the approver applies the `history-scan-approved` label to the PR. The
  approver is the GitHub login in the `VELCRO_HISTORY_APPROVER` repository variable
  (Settings → Secrets and variables → Actions → Variables), which the owner must
  set; the login is never committed. While it is unset or empty nobody can approve.
  The labeled run approves only the head it ran for; a later push runs blocked
  again until the label is removed and re-applied. A label applied by anyone else
  approves nothing. Applying any other label, or changing the PR's base, also re-runs
  CI (including the product job) without approval, and that run becomes the head's
  latest result, so re-apply the approval label afterwards. A title or body edit runs
  no checks: `required` repeats the result of the newest full run for the same PR,
  base branch and head (next sections), so it neither clears a blocked head nor
  approves one, and a newer unapproved run is never overtaken by an older approved one.
- A merge group has no approval channel. GitHub builds the group's commit itself, so
  it is a new head that no label can name, and its scan of `main..group` has its own
  1,000-entry cap. No approval carries over to it. The queued commit is one squashed
  commit, whose changed files are at most those of the PR's range (often fewer, since
  repeated edits to a file count once), so a PR within the budget always fits. A PR
  whose squashed commit itself exceeds 1,000 entries cannot pass the merge queue,
  even when its PR range was approved. The owner decides how to land it (for example
  by splitting it); agents stop and report.
- A post-merge run on `main` has no approval channel, so an approved range over
  1,000 entries fails there too. It does not gate Pages, which scans full history,
  and clears on the next push to `main` (a small range again).
- The pre-push hook reports every failure as `hook: required check failed`. To see
  whether it was exit 3, run `node scripts/security/git-privacy.mjs pre-push origin`
  (or `history origin/main..HEAD`) explicitly.
- A PR into a branch other than `main`, a force push, or a first push has no base
  that is the fetched `main` or its ancestor, so CI scans the full history under the
  hard caps instead of a range. A PR still meets the 1,000-entry budget against the
  fetched `main` first, so targeting another branch and later retargeting to `main`
  cannot skip approval; a base change is an `edited` event and re-runs CI.

Approval lifts only the 1,000-entry cap. Every finding, identity, protected-path,
archive and scanner check still applies, as do the scanner's hard size and 10,000-entry caps.
Full-history mode (`history <tip>`, used by the Pages deployment) does not use the
1,000-entry cap: its count grows with the whole project and it is not a newly
published range.

Source publication supports UTF-8 regular text files only. Archives, binaries,
symlinks, submodules, runtime material, tags and broad ref pushes are not certified.
Content is bounded and secret-scanned with numbered text names so stock path
exclusions cannot hide lockfiles or other source files. This is not a general
release-archive processor. Build/pack output is local-only, not publication-approved.
No package or test output is uploaded. CI uploads one workflow artifact, `product-build`:
the library and docs build output that the later CI jobs test, kept for one day. It is
scanned with the privacy rules and the pinned Gitleaks engine first, and only the
scanned bytes are uploaded (`scripts/ci/scan-build-output.mjs`). The Pages workflow
also uploads the prepared site for deployment (`docs/deployment.md`).

## Hooks are explicit and shared

Hook files are checked even when not installed; absence is never a successful
check. Do **not** install while parallel worktrees lack the same engines and
pinned scanner. After the manual initial trust anchor exists, coordinating all
lanes and obtaining independent human review, use
`pnpm hooks:install` to opt in with repository-local `core.hooksPath=.githooks`.
The installer refuses a missing or symbolic fetched main baseline. That setting
is shared across worktrees. It never changes global configuration.
The three executable shell hooks omit interpreter paths and use Git's shell
fallback; they run identity/staged, message, and proposed-OID guards respectively.
Hooks are bypassable and never replace explicit checks before outbound operations.

## Local development history versus publication

Clean local commits require current-file privacy/secret checks, exact staged-object
and effective-identity checks, message checks, and tests. They do not certify every
ancestor of a private development branch. Pre-commit checks staged source;
pre-push checks the proposed tip's ancestry metadata and the files its new commits change. Never substitute one result for the
other or add a skip-history switch.

Keep private development history intact. Obsolete detector/test snapshots may
continue to trigger privacy rules even after current source is corrected. Before
first publication, the coordinator must construct a separately reviewed clean
publication branch from the sanitized initial root and reviewed current tree.
Scan that exact proposed public ancestry explicitly with `history <tip-oid>` before
any outbound operation. A clean working tree, clean staged result, or local
development commit is not publication approval. Classify findings privately as
real sensitive values versus detector/test literals; do not broaden exceptions or
rewrite every active branch merely to silence history checks.

## Manual first-publication trust anchor

The first public main cannot depend on a fetched baseline that does not yet exist.
There is deliberately no bootstrap-approval flag or alternate unscanned push path.
Before the repository exists, the owner/coordinator must independently review the
clean export, select the single allowed initial `refs/heads/main` and its full OID,
and explicitly authorize
that exact initial publication. Freeze those refs and run trusted `history <oid>`
for every proposed public tip, with the same source, secret, author/committer,
message and complete ancestry checks used for routine publication. Verify the
frozen ref-to-OID mapping again immediately before the authorized operation; any
change invalidates the evidence and approval. Scan outbound text separately too,
with `artifacts.mjs` on the exact final bytes (plain text only).
Nothing in this document authorizes an outbound command or claims GitHub controls
already exist.

Required hooks are installed only after the clean main exists and its separately
authorized fetch establishes the trusted `origin/main` ref. A local ref's existence
does not prove its origin or human approval; that initial trust is the owner's
explicit external responsibility. Future authorized fetches update the anchor;
routine feature pushes must include that known main. The routine pre-push guard
still rejects direct main updates. Bootstrap publication and later GitHub web
merges are distinct operations, not disabled privacy checks.

## Historical platform metadata

Local effective author and committer must always equal the owner identity in the
trusted policy. Raw historical commits additionally permit only the canonical
GitHub web-merge **committer** pair encoded in the guard: name `GitHub`, email
assembled as `['noreply', 'github.com'].join('@')`. This is a narrow public-platform
metadata exception, not an email-domain allowance. GitHub is not an allowed author;
mismatched names, emails and roles fail. Messages, footers, source and filenames
receive no platform-email exception. Metadata alone does not authenticate that
GitHub created a commit.

A merge-queue squash cannot set its author email: GitHub uses the PR author's
commit email setting. Before the queue is relied on, the owner confirms that the
account's commit email is the approved noreply address ("Keep my email addresses
private"). The merge tooling checks the queued commit with the history guard
before marking it (below), so a wrong author or message stops the merge rather
than landing on `main`. An unexpected author/footer or platform pair is a blocker;
do not broaden the exception to make a generated commit pass.

## Merge queue and agent approvals

`main` lands only through GitHub's merge queue. A pull request needs two checks,
on its head and again on the commit the queue builds:

- `required`, from GitHub Actions: the CI aggregate (next section). The queue runs
  CI on a `merge_group` event for its commit, which is `main` plus the squashed PR,
  so what is tested is exactly what lands.
- `agent-approvals`: a commit status the coordinator sets with
  `scripts/merge/agent-approvals.mjs` after two agent reviews approved that exact
  head.

What `agent-approvals` proves is limited. The ruleset accepts it from any source,
because a user token's status has no app to pin. So any account with write access
can set it, and so can a workflow that requests `statuses: write`. That includes a
workflow that a same-repository PR adds or edits: its `pull_request` run, and its
`merge_group` run, use the PR's workflow files. Fork PRs are capped to read-only
tokens. The committed workflows request no such permission (a test checks the
current files), but that cannot bind a future PR. Two things stand behind the
status:

- The coordinator is the only one who enqueues. Before marking a commit, the script
  refuses if that commit already carries an `agent-approvals` status from any other
  account (a `github-actions[bot]` token, for example). Afterwards it confirms that
  the newest status for that context is its own success.
- Every change under `.github/workflows` is a protected change. It needs the
  independent human review (above) before it is merged. The CI policy step only
  reports such changes; detection is not approval.

The coordinator keeps a binding for each PR outside the repository:
`{ "head": "<full OID>", "approvals": 2, "reviews": ["<report>", ...] }`, with
report paths relative to a root it names. The script refuses unless the head is
the exact full OID it was asked to mark, there are at least two reports and exactly
`approvals` of them, and each report is a distinct regular file inside the root
whose first line is `APPROVED` and which names the approved head's full OID, so a
report from an earlier round is never reused for a new head. Reviewers therefore
state the full head OID they reviewed. The binding itself is the coordinator's
attestation: the script cannot prove who wrote a report. It prints fixed lines with
OIDs only.

```sh
node scripts/merge/agent-approvals.mjs check <binding> --head <oid> --root <dir>
node scripts/merge/agent-approvals.mjs set <binding> --head <oid> --root <dir> --repo <owner/name> --pr <n>
node scripts/merge/agent-approvals.mjs set-group <binding> --head <oid> --root <dir> --repo <owner/name> --pr <n> --group <oid>
```

`set` marks the PR head, after confirming the PR is open, not a draft, targets
`main` from the same repository and still has that head. It also lets the PR join
the queue. `set-group` marks the queue's commit for that PR as GitHub reports it:
the PR's `mergeQueueEntry` (GraphQL), never a branch name derived from the head.
GitHub names the queue branch after the base it was built on
(`gh-readonly-queue/main/pr-<n>-<base oid>`). The entry must be awaiting checks for
the approved head and built on the current `main` tip. Its commit must be the
`--group` commit the caller scanned, have that tip as its single parent and exactly
the approved head's tree, and the head must already contain that tip. The queued
commit therefore lands nothing but the approved content. A push to the PR removes
it from the queue and needs a new binding. A queue rebuild has a new commit, which
`set-group` must check again.

The merge sequence is: confirm the PR is up to date with `main` and `required` is
green on its head, run `check`, run the privacy checks on the head and the merge
title, `set`, then enqueue it bound to the head (GraphQL `enqueuePullRequest` with
`expectedHeadOid`). When the PR's `mergeQueueEntry` reports its `headCommit` (the
group commit), fetch the PR's queue branches (`gh-readonly-queue/main/pr-<n>-*`) and
run `node scripts/security/git-privacy.mjs history <main>..<group>` on that exact
commit, which checks its author, committer and message as well as its content. Then
run `set-group --group <group>`, which refuses if the queue has since rebuilt the
entry. If the guard fails, dequeue instead (`dequeuePullRequest`). After
GitHub reports `MERGED`, confirm the merge commit is the group commit that was
marked. Never use an admin merge or a ruleset bypass to skip the queue.

### Branch rules on `main`

The owner applies these settings. The workflow cannot enforce them. Use one
repository ruleset (`POST /repos/{owner}/{repo}/rulesets`) with these fields:

| Field | Value |
| --- | --- |
| `target`, `enforcement` | `branch`, `active` |
| `conditions.ref_name` | `include: ["~DEFAULT_BRANCH"]`, `exclude: []` |
| `bypass_actors` | `[]`: no routine bypass, so no admin or owner merge around the queue |
| rule `deletion` | present |
| rule `non_fast_forward` | present |
| rule `pull_request` | `required_approving_review_count: 0` (the owner is the only author and cannot approve their own PR; `agent-approvals` replaces the review), `dismiss_stale_reviews_on_push: false`, `require_code_owner_review: false`, `require_last_push_approval: false`, `required_review_thread_resolution: true`, `allowed_merge_methods: ["squash"]` |
| rule `required_status_checks` | `required_status_checks: [{ "context": "required", "integration_id": 15368 }, { "context": "agent-approvals" }]`. 15368 is GitHub Actions. `agent-approvals` has no `integration_id` ("any source"), because it is a commit status from the owner's token, not an app. Also `strict_required_status_checks_policy: false`, because the queue tests on the latest `main`, and `do_not_enforce_on_create: false` |
| rule `merge_queue` | `merge_method: "SQUASH"`, `grouping_strategy: "ALLGREEN"`, `max_entries_to_build: 1`, `min_entries_to_merge: 1`, `max_entries_to_merge: 1`, `min_entries_to_merge_wait_minutes: 0`, `check_response_timeout_minutes: 60` |

Set the Actions workflow permissions
(`PUT /repos/{owner}/{repo}/actions/permissions/workflow`) to
`default_workflow_permissions: "read"` and `can_approve_pull_request_reviews: false`.
This narrows the default token. A workflow can still request `statuses: write`
explicitly, which is why workflow changes need human review (above).

Then delete the classic branch protection on `main`
(`DELETE /repos/{owner}/{repo}/branches/main/protection`). Its review requirement
and strict up-to-date check would conflict, and the owner's review bypass would
remain a routine bypass. In the repository settings, set
`squash_merge_commit_title: "PR_TITLE"` and `squash_merge_commit_message: "BLANK"`,
so a queued commit's message is only `<title> (#<n>)`. Keep `allow_squash_merge: true`.
`set-group` requires a single entry per group, built directly on `main`. A larger
group fails closed: it gets no `agent-approvals` status and times out of the queue.
The coordinator's merge tooling checks these rules before it enqueues anything.

## CI and trust limitations

CI pins actions, Node and pnpm; public-npm frozen install remains required. The
`required` aggregate runs with `always()` and accepts exactly `verify`, `product`,
`site` and `security` with successful results. Missing, skipped, failed or cancelled jobs
block. CI runs on pushes to `main`, on PRs and on merge-queue `merge_group` events.
The one exception is a PR title or body edit, which changes neither head nor base.
There every analysis job is skipped and `required` repeats the result of an earlier
run. A PR run's name records its PR number, base branch and mode:
`CI pr <n> into <base> (full)`, or `(repeat)` for an edit. `required` lists this
workflow's `pull_request` runs for the head, keeps only full runs for this PR and
base branch, and takes the newest by run number, which is creation order, never
completion time. It passes only if that run completed successfully, and it prints
the run it repeats. A newer full run that is pending or failed therefore blocks.
That includes a retarget or label run, or a re-run in progress, even when an older
run succeeded later. A run for another base, another PR or a repeat run is never
evidence. Listing runs needs `actions: read`, the only permission beyond read-only
contents. It also blocks if no such run exists, the listing is unreadable, or any
job was not skipped. GitHub counts a skipped required check as passing, so
`required` itself is never skipped. When the base branch's tip moves, CI does not
re-run, with or without edits; the merge queue re-tests on the current `main`. Security scans PR objects with engines from the base checkout, not
candidate-modified engines; a base lacking the guard fails closed.

The pinned Gitleaks archive is cached with `actions/cache` so a GitHub release-CDN
outage does not fail every job. The cache key is the pinned version, the runners'
target (`linux-x64`) and that target's pinned archive SHA-256, with no fallback keys,
and the cached path is only the installer's `archives/` directory. A hit is untrusted
bytes: the installer re-verifies it against the pinned SHA-256 before extracting
anything, then the executable against its own pinned SHA-256 and version; wrong bytes
fail the job and are never replaced by a download. A miss falls back to the pinned
download, unchanged, and keeps the archive only after it verified. GitHub scopes caches
to the branch that wrote them, so a PR or merge-group run can read its own entries and
`main`'s, but runs on `main` (pushes and Pages) read only `main`'s. A candidate can
poison only its own run's cache, and the checksum then fails that run. The `security`
job restores no cache at all: a restore unpacks an archive that candidate code can
write, which could overwrite the base-owned engines that job certifies with. It
therefore always downloads, and it alone opts in (`VELCRO_GITLEAKS_DOWNLOAD_RETRY=1`)
to a bounded retry of transport failures only: network errors, timeouts and HTTP
5xx. It makes at most 4 attempts, waits 5, 10 and 20 seconds between them, and caps
each attempt at 30 seconds and all attempts and waits together at 2 minutes. Each
attempt downloads into a fresh temporary file that is removed afterwards and checked
against the pinned SHA-256 before use. A checksum mismatch, any other HTTP status or
an oversized download fails at once and is never retried. A longer outage can
still fail the job. Because the job runs the base's installer, the retry applies
only once the base has it; an older base ignores the variable and downloads once.
The other downloads in CI are pinned by version but not by our own checksum: Node
(`setup-node`), pnpm (`pnpm/action-setup`), npm packages (lockfile integrity) and
Playwright browsers (cached by lockfile hash, as before).

Protected changes are reported for a separate, mandatory human merge/publication
gate; green data checks do not satisfy that gate. Candidate policy files are
scanned as data with base-owned rules, never adopted as active policy. Exact owner
identity and standard interpreter metadata in the supported policy schema are
recognized without exempting arbitrary field values or new exception targets.
Malformed/unsupported policies fail conservatively. There is no self-approval
environment flag. Independent human review and a separately approved trusted-base
transition remain necessary for bootstrap and future protected updates. A base
without the scanner is an explicit manual initial CI-trust transition, not an
always-green substitute job. The current public commit identity does not provide a
separate PR author; native GitHub self-approval is not possible. Workflow changes
can also change the workflow gate itself, so external rules/review controls must
be installed and proven on GitHub before claiming enforcement. Local tests do not
prove remote CI, rulesets or approval behavior. First push and all publication
remain blocked pending full source/history checks, independent review and explicit
authorization. Never bypass a failed scanner or missing approval.
